# TodoPay 금융 처리 안정성 운영 기준

## 적용 범위

이 문서는 코리아결제시스템(KP Pay) 입금 NOTI, 지급이체 요청, TodoPay 원장·잔액,
관리자 인증 및 AWS 경계 보안의 운영 기준을 설명한다. 비밀 키와 개인정보는 기록하지
않는다.

## 입금 처리

1. `112.175.152.181`에서 전송된 KP Pay POST NOTI만 애플리케이션에서 허용한다.
2. ALB WAF는 위 IP와 `/api/webhooks/kp-pay/` 경로가 모두 일치하는 요청에 전용
   허용 규칙을 적용한다. 일반 API의 IP별 속도 제한은 유지한다.
3. 수신 요청은 `payment_events`에 먼저 영속화한다. 이미 저장된 공급자 이벤트 ID는
   유니크 제약으로 중복 저장하지 않는다.
4. DB 저장이 성공한 뒤에만 PG에 성공 응답을 반환한다.
5. 워커는 `FOR UPDATE SKIP LOCKED`로 이벤트를 점유하고 원장, 거래, 잔액을 하나의
   DB 트랜잭션으로 반영한다.
6. 처리 실패는 지수 백오프로 재시도하고 최대 시도 횟수 초과 시 `dead` 상태로
   격리한다. 플랫폼 운영 API에서 재처리할 수 있다.

Redis는 속도 제한과 보조 큐에 사용하지만 금융 처리의 진실 공급원은 PostgreSQL이다.
따라서 Redis 재시작이나 캐시 유실이 입금 원장 유실로 이어지지 않는다.

## 출금 처리

1. 승인된 출금은 API 요청 스레드에서 PG로 바로 전송하지 않고 `unpaid`로 큐잉한다.
2. 출금 워커가 DB 원자적 점유 후 `submitting`으로 전환하고 PG 요청을 한 번 수행한다.
3. PG가 명시적으로 거절한 요청만 제한적으로 재시도한다.
4. 타임아웃, 연결 단절, 성공 응답 파싱 실패처럼 실제 처리 여부를 판단할 수 없는
   경우에는 자동 재전송하지 않고 `unknown`으로 격리한다.
5. KP Pay 가이드에는 건별 지급이체 결과 조회 API가 없으므로 `unknown` 건은 PG에
   거래번호로 확인한 뒤 운영자가 확정한다. 확인 없이 재전송하면 이중 출금 위험이 있다.
6. PG 출금 NOTI는 `submitting` 상태의 요청도 정상 완료시킬 수 있다.

## 대사와 복구

15분마다 다음 항목을 자동 대사하고 결과를 `reconciliation_runs`에 남긴다.

- 원장 합계와 저장 잔액 불일치
- 거래 금액과 원장 금액 불일치
- 장시간 `processing`인 입금 이벤트
- 장시간 `submitting`인 출금
- `dead` 입금 이벤트
- KP Pay 가맹점 집계 잔액 조회 결과

운영 API:

- `GET /api/platform/financial-integrity`
- `POST /api/platform/financial-integrity/run`
- `POST /api/platform/payment-events/:eventId/retry`

장애 시에는 먼저 입금 이벤트와 출금 상태를 확인한다. `unknown` 출금은 자동 재처리하지
않는다. `dead` 입금은 원인 수정 후 운영 API로 재처리한다.

## 관리자 보안

- 플랫폼·파트너 관리자는 RFC 6238 TOTP MFA를 등록할 수 있다.
- TOTP 비밀은 `SESSION_SECRET` 기반 AES-256-GCM으로 암호화하여 저장한다.
- 동일 TOTP 시간 단계의 재사용을 차단한다.
- 금융 승인·출금 큐잉에는 `X-TodoPay-OTP` 헤더가 필요하다.
- 로그아웃, 비밀번호 변경, MFA 변경 시 중앙 세션 버전 또는 Redis 폐기 목록으로 기존
  세션을 무효화한다.
- 관리자 로그인에는 IP·계정별 속도 제한을 적용한다.

## AWS 운영 경계

- AWS WAF: 관리형 공통 공격, 알려진 악성 입력, IP 평판, 일반 API 속도 제한
- CloudTrail: 다중 리전 이벤트 및 로그 파일 무결성 검증
- GuardDuty 및 Security Hub
- ALB/WAF 접근 로그
- ALB 5xx, 비정상 타깃, RDS CPU·메모리, Redis eviction, 금융 이상 로그 경보
- CloudFront CSP, HSTS, frame 차단, MIME 스니핑 차단, referrer 제한

SNS 경보 토픽은 생성되어 있다. 이메일 구독은 수신자 승인과 명시적 운영 동의 후
별도로 연결한다.

## 2026-07-29 검증 결과

통합·동시성 검증:

- 동일 이벤트 50회 동시 입력: 잔액 반영 1회
- 트랜잭션 중간 실패: 부분 원장 반영 없음
- 동일 출금 동시 점유: 워커 1개만 승자

격리 DB 부하 검증:

|---:|---:|---:|---:|---:|---:|---:|
| 100 | 91 | 9 | 0 | 1,448/s | 67ms | 68ms |
| 500 | 451 | 49 | 0 | 1,674/s | 148ms | 155ms |
| 1,000 | 901 | 99 | 0 | 3,188/s | 67ms | 71ms |

이 결과는 운영 RDS에서 임시 격리 테이블로 측정한 DB 인박스·중복 방지·원장 핵심
경로 결과다. PG 외부망의 실제 지연과 HTTP 종단 부하는 포함하지 않는다. 실제 PG
소액 테스트 승인 후에는 입금, 중복 NOTI, 출금 성공, 출금 타임아웃, NOTI 재전송
시나리오를 순서대로 검증한다.
